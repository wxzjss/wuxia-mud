## 〇、三句话

1. **是什么**：一个"点了才知道该敲什么"的提示系统 —— 房间描写里的名词被点亮，玩家伸手去点，游戏才告诉他这个动作叫什么。
2. **玩家做什么**：看房间 → 看见一个跟别的不一样的词 → 点它 → 看见"对它做什么" + "也可以心里默念『XX』" → 下一次不用点，直接敲。
3. **爽点在哪**：**游戏从不主动教你，只在你伸手时回答你。** 教完一次就闭嘴。

## 一、核心设计概览

### 1.0 先说结论：四个问题的答案

| 主人问的 | 我的裁定 |
|---|---|
| **① 哪些名词该做成可交互？** | **有 action 数据的、此刻能用的、且不滥的。** 判据是"数据闸门"，不是"剧情需要"，也不是"有对应指令"。详见 §2 |
| **② 提示怎么写才不像说明书？** | **分三层，只有第三层才出现指令名，且指令名一律装在「心里默念『XX』」这个壳里。** 详见 §3 |
| **③ 怎么顺着剧情走？** | **提示不主动出现，只在玩家伸手后出现。** 吸引靠内容，教法靠点击。详见 §4 |
| **④ 什么时候不给提示？** | **玩家手敲过这个指令 ⇒ 永久闭嘴。** 详见 §5 |

### 1.1 🔴 先解决一处正面冲突：`design/72` 明令禁止键盘提示

`design/72:698` 那张「I.1 不可出现的四件事」里有这么一行：

| 不要 | 替代 |
|---|---|
| 「按 look」这类键盘提示 | 让房间第一句就给出吸引点（水缸在挡路） |

而主人这次明确要求「提醒玩家应该输入什么指令」。**这两条是打架的。** 不把它说清楚，下一个接手的人必然二选一改错。

我的裁定 —— **「教」和「助」是两件事，分水岭是"谁先伸手"**：

| | 谁先开口 | 玩家此刻的状态 | `design/72` 的态度 |
|---|---|---|---|
| **教**（教程） | **游戏先说** | 还没有欲望 | ❌ 明令禁止，维持 |
| **助**（提示） | **玩家先伸手**（点了一下） | 已经想做、只是不知道叫什么 | ✅ 新增，允许 |

⇒ 所以本文定的第一条硬规矩是：

> 🔴 **屏幕永不主动写出一条指令。**
> 屏幕能主动做的只有一件事：**把那个词点亮。**
> 指令名只在玩家点了之后才出现。

这样 `design/72` 那条禁令一个字都不用改 —— 它没有禁"回答"，它禁的是"催促"。
而主人的要求也满足了 —— 点一下就知道该敲什么。

**一句话**：吸引靠内容（`design/72` 已定），教法靠点击（本文新增）。

## 二、哪些名词该做成可交互

### 2.1 判据：三条同时成立

| # | 判据 | 为什么 |
|---|---|---|
| **① 数据闸门** | `room.actions[]` 里有它，且 `a.cmd` 写好了 | **硬闸门。** 没有数据支撑的高亮 = 点了没反应 = 本项目最忌的静默失效 |
| **② 此刻能用** | `a.cond` 通过 / 限次没到 / 不在战斗中 | 点下去得到一句「现在做不了这个」是高亮自己打自己的脸 |
| **③ 不滥** | **房间描写里的可交互名词 ≤ 2 个** | 全高亮 = 一片花 = 等于没高亮 |

### 2.2 两条我明确**否掉**的判据

**❌ 否掉「它真的有对应指令」。**

理由有两个，都是核过的：
- 房间 action 的 `cmd` **可以是任意字符串**，不受内置指令表限制。`commands.js:5650-5661` 的 `questKeyword` 是拿**整串**去比（`ac === full`），`tokenize('端碗')` 得到 `['端碗']`（中文无空格，`utils.js:90-107`），所以**主人举例的「端碗」今天就能实现**，路径是房间 action + `cmd:'端碗'`，不需要注册任何新指令。
- 反过来，`look` / `get` 能作用于任何名词。用它当判据 ⇒ 全高亮。

**❌ 否掉「剧情此刻需要玩家对它做什么」（单独用）。**

剧情需要但没人做 ⇒ 点了没反应 ⇒ 比不提示更糟，因为它证明游戏在骗人。

**剧情的正确位置是：排序依据，不是准入依据。**
排不出先后就按 `room.actions` 的原序取前 2 个。

### 2.3 三档

| 档 | 是什么 | 高亮 | 提示 | 数量 |
|---|---|---|---|---|
| **甲档 · 剧情件** | 第一章主线点名的那一件（缸 / 碗 / 引荐信），或带 `cond` / `once` 的一次性动作 | ✅ | 完整三层，且不按次数衰减（因为它本来就只发生一次） | 第一章 **8–12 条** |
| **乙档 · 常驻件** | 其余 256 条房间 action（打水 / 说书 / 典当…） | ✅ | 只给 L2 + L3 一次 | 全库 |
| **丙档 · 地上物 / NPC / 出口** | `这里有：` / `地上散落着：` / `出口：` | 维持现状 | **不动** | — |

**为什么丙档不动**：那三行本来就是**清单**（「地上散落着：铜钱、干粮。」），玩家看得懂"这是可以拿的东西"。它们不需要"嵌在语境里点"，它们已经在语境里了。动了反而破坏现有手感。

### 2.4 「主角位」的落地办法：自动匹配（**点亮这件事**不新增字段）

```
room.actions[].label = '缸'
room.desc = '……缸挡着灶膛。老汉侧了十九年。'
⇒ 渲染描写行时拿 label 去 desc 里 indexOf，命中就点亮
```

- **点亮这件事零新增字段**，229 间房里大部分自动亮起来。
- 前端 `renderLogText`（`ui.js:540-545`）用的是 `raw.indexOf(needle)` + **只替换一次** ⇒ desc 里"缸"出现三次，**只亮第一个**。这个行为是对的（少即是多），保留。
- 误伤时（desc 里的"缸"说的不是那个 action）用 `inDesc: false` 显式关掉。
- ⚠️ **本次新增的字段是两个，不是零个** —— `inDesc`（点亮用）+ `say`（提示文案用）。
  `say` 是 §7.2.1 那 96 条逼出来的，**不是点亮这件事要的**。别把两件事混在一起砍。

### 2.4.1 🔴 同一个动作亮两处怎么办（甄塑之 `82/N-V-23` 要我拍的那条）

甄塑之在视觉规格 §3.5 提了一条硬约束，把决定权留给我：

> **同一动作不许在两处高亮。** 描写里的「碗」和「此地可做」那一行里的「碗」
> **不能同时是 `.hl`** —— 那是同一件事亮两次，就是主人已经报过一次的"屏幕上有两个此地可做"。

**我的裁定：保留描写里的那一处，「此地可做」行里那一个不再高亮，但文字保留。**

| | 描写行 | 「此地可做」行 |
|---|---|---|
| 高亮 | ✅ 保留 | ❌ 剔掉这一个 |
| 文字 | ✅ | ✅ 仍在清单里列出 |

**三条理由：**

1. **主人的原话指的就是描写里的词** ——「面前有个碗……这个『碗』的文本颜色会与其他做出区别」。他要的是描写里的那个碗，不是清单里那三个字。
2. **「此地可做」行本来就是清单**（「此地可做：挪缸、舀水、掏灰。」），整行都是可点项，它不需要再靠高亮告诉玩家"这个能点"。
3. **主人已经为"同一件事显示两遍"报过一次 bug**（「屏幕上有两个此地可做」）。这一条如果放开，就是同一个病换个地方再犯一次。

**执行办法**：`inDesc` 不为 `false`、且 `label` 在 `desc` 里命中的 action ⇒ 从「此地可做」行的 `hl` 数组里剔除，**但 `names` 文字列表不动**。
⇒ 多动作房（20 间）可能出现"描写里亮 2 个、清单行里剩 1 个可点"的状态，这是对的。

## 三、提示怎么写才不像说明书

### 3.1 核心手法：把指令名装进「心里默念」这个壳

这个游戏**本来就有**一个说法 —— 未知指令的兜底回执是：

> 「XX」是什么指令？**你可以在心中默念「help」看看都会些什么。**（`commands.js:5634`）

**「心里默念」是项目现成的世界观说法。** 我不新造容器，直接借：

> 也可以**心里默念**「挪缸」

这就不是说明书了 —— 这是**角色的内心活动**。同一件事，两种写法：

| ❌ 说明书 | ✅ 本文定的写法 |
|---|---|
| （可交互：碗）输入指令：端碗 | 也可以心里默念「端碗」 |
| 【提示】你可以输入「挪缸」来完成此操作 | 下一次，心里默念「挪缸」就行 |
| 碗（可拿取）· 命令：get bowl | 心里默念「端碗」 |
| 点击此处或输入 endbowl | — |

### 3.2 三层提示（L1 / L2 / L3）

| 层 | 什么时候出现 | 要不要点 | 说什么 | 归谁 |
|---|---|---|---|---|
| **L1 点亮** | 每次渲染房间描写 | 不用 | **一个字都不说**，只把那个词变成可点的样子 | 视觉：甄塑之 `81-interactive-noun-visual.md` |
| **L2 提示行** | 第 1 次点那个词 | 要点 | 提示行：动作名 + 人话后果 + **可点的指令** | 视觉归他，文字归本文 |
| **L3 回执教** | 执行之后 / **失败之后** | 不用 | 一次「下一次，心里默念『XX』就行」 | 文字：本文 |

⚠️ **L2 的形态以甄塑之的视觉规格为准** —— 他定的是"紧贴那一行的行内展开提示行"，
**不是**弹窗菜单。我原稿写的"菜单底栏默念句"作废，改成提示行两颗槽位（见下）。

**三层的分工一句话**：L1 负责"这里有东西"，L2 负责"对它做什么、该敲什么"，L3 负责"下次不用点了"。

### 3.2.1 提示行的两个槽位：我填什么

甄塑之在视觉规格里留了两个槽位，**这两个槽位填的不是同一个字段**：

| 槽位 | 填什么 | 字段 | 约束 |
|---|---|---|---|
| `.hl-tip-cmd` | **显示**：玩家该敲的那串字 | **`say`** | ≤6 字；不撞 PANEL_CMDS |
| `.hl-tip-cmd` 的 `data-cmd` | **执行**：机器认的那串 | **`cmd`** | 🔴 **绝不能填 `say`** |
| `.hl-tip-note` | 一句话说明 | **`desc`** | ≤**12** 字（他给的上限是 20，我收紧到 12，见 §5.3） |

🔴 **`.hl-tip-cmd` 的显示文字与 `data-cmd` 必须分开，这是 96 条 `cmd` 逼出来的：**
`data-cmd` 要填 `sell` / `knock 登闻鼓` / `ask 脚夫 about 搬运`（机器认的），
显示文字要填「典当」/「击鼓」/「问脚夫」（人看的）。
**拿 `say` 去填 `data-cmd`，后端认不出来** —— 这是 §8.2.2 那条断言的前端形态。

⇒ 给甄塑之补一条断言：**`data-cmd` 必须逐字等于 `cmd`；`panelForCmd(cmd)` 为 null；且 `say === cmd || keywords.includes(say)`。**
（他现有的 `82/N-V-14` 只判了 PANEL_CMDS，挡不住这一条。）

### 3.3 🔴 209 间房的洞怎么补 —— 这里我和甄塑之的视觉规格撞了，以他的为准

`ui.js:574-577` 写死了：**只有一个动作 ⇒ 直接执行，不弹窗。**
全库 229 间有 action 的房间里 **209 间只有 1 条 action** ⇒ 今天这 209 间点了就干，一句话都不说。

**我第一版的解法是"执行后追加一句"（L3 兜住）。甄塑之的 `design/81-interactive-noun-visual.md` §0.3 否了这条，他的理由比我的硬：**

> 主人要的是"点击这个文本时**会提醒玩家应该输入什么指令**"。
> 今天只有一个动作时（「碗」→「端碗」正是这种），**点了就直接端了，一句话都不说**。

**⇒ 他对，我改。**「点了不说话」直接违背主人那句原话，而"不打断"只是我的偏好，不是需求。

### 3.3.1 合并后的点击时序（两张方案的合流）

| 第几次点这个词 | 发生什么 | 出不出提示 |
|---|---|---|
| **第 1 次** | **展开提示行，不执行**（含可点的指令） | **L2 提示行** |
| 点提示行里那颗指令 | 执行 | 执行后追加 **L3 一句** |
| **第 2 次及以后** | **直接执行**（不再展开） | 无 |
| 玩家手敲过这个指令 | **直接执行** | 无 |

⇒ **总曝光次数不变**（一条指令从"不认识"到"闭嘴"，全程最多 2 次文字），
但**第一次点击是"先告诉、再让你做"** —— 主人的话兑现了，§5.4 的噪音自检结论也不变。

⚠️ 给寇豆码/严过关：**甄塑之的 `82/N-V-21`（点后 100ms 内不得发 `/api/exec`）只对"第一次点"成立**，
第二次点直接发。**判据要带"首次"这个条件，别写成一刀切。**

### 3.3.2 L3 现在的定位：补"下一次"这个词

L3 不再是补 209 间房的洞（那洞由 L2 提示行补了），而是**把"点"变成"敲"的那一步**：

```
> 挪缸
你蹲下去，把手掌贴着缸沿底下往里插。指腹先碰到一层滑腻的东西，是青苔。
（下一次，心里默念「挪缸」就行）
```

### 3.4 失败时给的是**下一条路**，不是安慰

这是三层里最有价值的一条，也是本项目一贯的哲学（「不报错、只是静默走错路」那一族）：

```
指尖勒出一道白印，印子过了一会儿才慢慢发红。
老汉看了你一眼，没说话。
（缸太沉，先倒掉些水会轻些。心里默念「舀水」）
```

**失败提示直接指向下一条指令。** 玩家此刻卡住了，这时候指路最有用。

⇒ 规则：**甲档 / 乙档的 action 只要有 `failMsg`，就要再给一条 `next`** ——
`failMsg` 写「为什么不行 + 下一步该干什么」，`next` 写下一步那条指令的 `say`，
「心里默念「XX」」这层外壳**由程序生成、另起一行**，不写进 `failMsg`。

### 3.4.1 为什么外壳不由人手打进 `failMsg`（第 5 处自我更正的落法）

原稿写的是「`failMsg` 已有的 41 条照抄前半句，补后半句」。**实写第一章三件时这条站不住：**

| 问题 | 具体 |
|---|---|
| 同一件事说两遍 | `failMsg` 出一遍「缸太沉…」，L3 再出一遍「缸太沉…心里默念「舀水」」。玩家看到两条一样的抱怨 |
| 外壳会被人手打歪 | 「心里默念」四个字要打 N 遍，迟早打成「默念」「念念」「心里念」，文案统一性立刻散 |
| 🔴 最要命的 | 人手打的指令名**不受 §6.5 铁律管** —— 打出一个不在 `keywords` 里的词，玩家照敲就是「『XX』是什么指令？」 |

⇒ 所以拆成两层：**`failMsg`（数据，叙事层，人写）+ `next`（数据，一个词）+ 外壳（程序生成，统一）**。

```
缸太沉，手指嵌进去一截，拔不出来。先倒掉些水会轻些。   ← failMsg，kind: warn
（心里默念「舀水」）                                    ← 由 next 生成，kind: hint
```

**为什么另起一行而不是接在同一句后面**：上半句是"江湖里发生的事"，下半句是"系统对玩家说的话"。
接在一起就成了「缸太沉，手指嵌进去一截，拔不出来。先倒掉些水会轻些。心里默念「舀水」」——
一句里先演戏再跳出来教学，破功。分成两行，玩家自己会跳过第二行。

### 3.5 文风：沿用 `design/77` 的**文风五戒**

提示句也是"房间描写 / 台词"这一级的短文本，照 §2.1 那张两行单位表，**按"不用"算，不按密度算**：

| 五戒 | 对提示句的具体要求 |
|---|---|
| 一 · 不作聪明观察 | 提示只说事，不抒情。❌「缸沉默地蹲在那里，像在等你」 |
| 二 · 要有短句 | 提示 ≤12 字 ⇒ 天然是短句，不要再塞从句 |
| 三 · 不在同一位置收尾 | 提示全篇统一收在「『XX』」上 ⇒ **这一戒对提示不适用，豁免**（提示是格式文本，不是描写） |
| 四 · 数字与具体名词 > 明喻 | 「三尺」「一桶」「先有条粗麻袋」这类 ⇒ 提示天生符合 |
| **五 · 不用破折号** | **提示句不用「——」**（§7 样例里的「——」是本文的说明符号，落库时要换成句号或逗号） |

⚠️ §7 的样例里我用「——」是为了排版分隔，落库文案一律 **`原因。心里默念「XX」`** 或 **`原因，心里默念「XX」`**，不写破折号。

⚠️ 口径边界：**戒五管的是「落进游戏的文字」**（房间描写、台词、提示句），**不管设计文档自己的说明文字**。
本文正文里的「——」是写给接手的人看的，不是落库文案 —— 与 `design/75` §1.10 那段"故意保留的反例"同一处理，
守卫扫的是 §7 与 §8 的落库区块，不是全文。

### 3.6 三条统一格式

1. **提示里出现指令名，一律用「」包住**，全篇统一，不用引号、不用反引号。
2. 🔴 **指令名照抄 `say` 字段（没有 `say` 才回落 `cmd`），一个字都不改。**
   `say` 写「挪缸」就写「挪缸」，不写「挪 缸」、不写「move gang」。玩家照着敲必须能成。
   ⚠️ **不要照抄 `cmd`** —— 全库 256 条 `cmd` 里有 96 条是 `sell` / `knock 登闻鼓` / `ask 脚夫 about 搬运` 这种，
   照抄会落出「心里默念「sell」」。详见 §7.2.1。
3. **全篇不出现方括号、尖括号、英文、冒号引导的标签。** 中文括号（）可以用。
   ⇒ 这一条**反过来就是 `say` 存在的理由**：`say` 的作用就是把 `cmd` 里的英文和空格挡在屏幕之外。

## 四、提示怎么顺着剧情走

### 4.1 一句话原则

> **提示不长在名词上，长在剧情节点上。**

同一口缸：
- **第一章辰时**（老汉肩膀卡住了）⇒ 点亮 + 提示
- **第三十天路过**（就是一口缸）⇒ **闭嘴**

⇒ 落地：**用 `a.cond` 和 `a.once` 判定"这一刻剧情在不在"。**
`cond` 不通过 / `once` 已经用掉 ⇒ 那个词根本不亮（`commands.js:5481 actionLimit` 已经有这套判定，直接复用）。

### 4.2 第一章是天然的新手教程（主人这条判断，我接，并给出施工图）

`design/72:688-700` 那张 I.0 时辰表已经是教程了 —— 它教的是**"发生"，不是"按键"**。
本文要做的是：**在每一刻玩家伸手的那个瞬间，把动作的名字递给他。**

| 时刻（`design/72` I.0） | 剧情在讲什么 | 玩家会伸手的那个名词 | 递给他的指令 | 用哪一层 |
|---|---|---|---|---|
| 卯时 · 老槐树·茶摊 | 看四周，这是哪儿 | — | `look`（**不提示**，这段纯看） | — |
| 辰时 · 挪缸 | 缸挡了路，不管走不了 | **缸** | `挪缸` | **L2 + L3（本章首条给 2 次）** |
| 辰时 · 倒水 | 缸太沉，得先倒掉些水 | **瓢** / **碗** | `舀水` | **L3 失败句**（缸太沉时） |
| 辰时末 · 引荐信 | 老汉指了一个具体的山名 | **老汉** | `talk 卖茶的老汉` | 丙档，不动 |
| 巳时 · 出南门 | 有人拦路要钱 | — | — | 不提示（NPC 对话自带菜单） |
| 午时 · 青溪村差事 | 村民请他带一句口信 | **村民** | 丙档，不动 | — |
| 酉时 · 独木桥（T-C） | 天暗了，过不去要露宿 | **桥** | `过桥` | **L2 + L3** |
| 戌时 · 小店歇一晚 | 累了、饿了 | **床** / **灶** | `住店` / `做熟` | **L2 + L3** |
| 亥时 · 给今天留句话 | 存档 + 一条记录 | — | `save`（**不提示**，这是人对自己做的事） | — |

**三处我明确"不提示"，理由写清：**

| 时刻 | 为什么不提示 |
|---|---|
| 卯时 看四周 | `look` 是输入框 placeholder 里唯一已经写了的东西（`index.html:205`），再教一遍是噪音 |
| 巳时 出南门 | 拦路要钱走的是 NPC 对话菜单，那条路本来就通，不用再教一遍 |
| 亥时 存档 | 「给今天留句话」是人对自己做的事，这时候跳出「心里默念 save」把气氛全毁了 |

⇒ **第一章 L2/L3 总曝光条数：8–12 条。** 超了就是噪音，砍。

### 4.3 为什么不给第一章加"教程专属提示"

因为 `design/72:686` 已经定了：**「不再有教程 —— 改为『你到达的这一天』」**。

本章的每一条提示，**形式上与第三十天路过大路时一模一样**，只是**触发它的剧情在第一章**。
玩家不会察觉自己在上教程课 —— 这正是主人要的"天然"。

## 五、什么时候不给提示

### 5.1 衰减总表

| 情形 | L1 点亮 | L2 提示行 | L3 回执教 |
|---|---|---|---|
| 第一次看见这个名词 | ✅ | — | — |
| 🔴 **第 1 次点这个词** | ✅ | **✅ 展开提示行，不执行** | — |
| 点提示行里那颗指令（= 第 1 次执行） | ✅ | 收起 | **✅ 追加 1 次**（甲档首条 2 次） |
| **第 2 次及以后点** | ✅ | ❌ **直接执行** | ❌ |
| 🔴 **玩家手敲过这条指令** | ✅ | ❌ **直接执行** | **❌ 永久关闭** |
| 战斗中 | ❌ | ❌ | ❌ |
| `once` 已用掉 / `cond` 不通过 | **❌（词都不亮）** | — | — |
| 玩家在设置里关了提示 | ✅ | ✅（提示行保留，那是"可点"的唯一入口） | ❌ |
| `oncePerDay` 当日已做 | ✅（仍亮，点了给 `dayMsg`） | ✅ | ❌ |

⚠️ **第 2 行是本节最要紧的一行**，它是 `design/81-interactive-noun-visual.md` §0.3 逼出来的。
我原稿写的是"点了直接执行、完了追加一句"，**那样主人的"点这个文本时会提醒我该输入什么"就没兑现**。

🔴 **注：L3 回执教只给"可重复"的动作。`once` 的动作不给。**

「（下一次，心里默念「XX」就行）」这句话里有个"下一次"。**`once` 的动作没有下一次** ——
写出去是句假话，而且假话还占一次曝光预算（§5.4 全程只给 2 次文字，浪费在假话上不值）。

**唯一例外：甲档首条。** 第一章辰时的「挪缸」是 `once`，照样给 L3 ——
因为它教的不是"挪缸"这两个字，是**"亮着的词原来可以直接敲"这件事**。
这件事全游戏只教一次，多给一次的成本 < 玩家三十天都没发现能敲的成本（§5.3 甲档首条 2 次，就是这么来的）。

### 5.2 🔴 最硬的一条：手敲过 ⇒ 永久关闭

提示的目的是"教"。**教完了就该消失。**

- 内置指令：现成的 `p.tutorialFlags` 已经在记（`engine.js:1975 markTutorial` → `flagForCommand` → `tut_` 前缀），`did_get` / `did_talk` / `did_look` 等十种标记今天**在记、不显示** —— 正好搬来当"关提示"的开关。
- ⚠️ **房间自定义 cmd（「挪缸」「舀水」）不在 `FLAG_BY_CANON` 表里**，走不了这条路。
  ⇒ 给寇豆码：**另开一本账 `p.hintSeen[roomId + '|' + cmd]`，不要往 `tutorialFlags` 里塞。**
  理由写在 §8 数据契约里 —— 下一个接手的人必须知道为什么分两本账。

### 5.3 数值区间（都给区间，说明调参依据）

| 项 | 区间 | 调参依据 |
|---|---|---|
| 房间描写里可交互名词上限 | **1–2 个**（推荐 1） | 全库单房 action 最多 3，≥2 的只有 20 间 ⇒ 取 2 是自然上限；再多就成清单 |
| L2 的 `hint` 字数 | **≤12 字**（现状均值 7.1，最长 19） | 19 字那条（「跟着伙计往后院去（当铺不声张的那一面）」）是菜单里最挤的一行 ⇒ 卡 12 |
| 默念句里的指令名 | **≤6 字** | 「挪缸」「舀水」「端碗」都 ≤2 字；留到 6 字是为了「看告示」「问那知客僧」这类既有 cmd |
| L3 曝光次数 | **1 次**（甲档首条 **2 次**） | 首条是全游戏唯一一次从零教，多给一次的成本 < 玩家卡住的成本 |
| 同一房间 L1 重新点亮的冷却 | **≥1 游戏日** | 复用 `p.actionLast`（`commands.js:5485`）的日期口径，不另起一套 |
| 第一章 L2/L3 总曝光 | **8–12 条** | §4.2 那张表数出来 5 处，含失败与分支共 8–12 |

### 5.4 噪音自检：会不会变成一直弹

按上表推一遍最坏情况（玩家全程只点、不敲）：

```
进房 → L1 亮 1 个词（不说话）
点击 → L2 弹菜单（1 次）
执行 → L3 追加 1 句（1 次）
再做  → 只有回执，没有 L3
```

## 六、🔴 `PANEL_CMDS` 避让（硬约束）

### 6.1 为什么这条是硬的

`ui.js:4110-4118`：`doCmd()` 第一件事就是 `panelForCmd(cmd)`，命中就**本地开面板、不发后端**。
`panelForCmd` 是 **整串精确匹配**（`ui.js:3861-3864`，`toLowerCase()` 后查表）。

⇒ **提示里写的指令串整串命中 PANEL_CMDS 的任何一个键 ⇒ 玩家照着敲，开的是面板，动作不发生。**

这正是本项目最忌的"静默失效"：玩家照做了，得到的是一个不相干的面板。

### 6.3 四条最容易撞的（它们长得最像江湖物件）

|---|---|---|

### 6.4 ⚠️ 第二层坑：动词也别用「看」

`utils.js:167-174` 的 `normalizeCmd` 有一条：

```js

// 命中后：rest 若为 NOUN_ALIAS 的键 → 直接返回那个标准指令
```

所以：

| 玩家敲 | `normalizeCmd` 变成 | 后果 |
|---|---|---|
| `看地图` | `map` | 后端返回地图文本（能看，但不是"看墙上那张图"） |
| `看背包` | `i` | 开背包 |
| `看状态` | `score` | 看自己状态 |
| `看武学` | `skills` | 看自己武学 |

⇒ **「看X」会被改写。** 玩家以为在看物件，实际在看别的东西。

**规则：提示里的动词用具体的，不要用「看 / 查看」。**
用：`端 / 挪 / 舀 / 翻 / 摸 / 掀 / 解 / 敲 / 端详 / 打量 / 摸索`。

（`打量` 已经被 NPC 菜单用了 —— `commands.js:781`，口径一致，可以沿用。）

⚠️ **例外：`cmd` 里本来就带「看」的既有条目不动。** 全库只有 `看告示`（`jiangnan_inn`）一条，
`panelForCmd('看告示')` 不存在 ⇒ 安全；改它反而会让老存档的宏指令失效。**新写的才守这条戒。**

### 6.5 🔴 铁律：不许提示一个不存在的指令

> **落提示之前，先把提示里那条指令串喂进 `execute()`，必须不落在第 8 步（未知指令）。**

`commands.js:5628-5637` 的兜底是：

> 「XX」是什么指令？你可以在心中默念「help」看看都会些什么。

⇒ **教了一个不存在的指令，比不教更糟** —— 它证明游戏在骗人，而且玩家会立刻发现。

**这条要写进守卫**（§9 需求 9）。判据可机械执行：
对每个 `room.actions[].cmd`，跑 `execute(cmd)`，断言返回的不是 `kind:'warn' && /是什么指令/`。

§7.1 给的是**单件的样子**，这里给**三件一起落库的全部文案**（`desc` / `failMsg` / `next` / `spentMsg` / L3）。

#### （一）三件互相卡着：失败句指向下一个

`design/74` §辰时 那五步（伸手 → 倒水 → 撬 → 垫 → 挪）在数据层收成三条 action。
**三条不是并列关系，是一条链** —— 每条的 `cond` 就是上一条做完没有：

| 顺序 | 动作 | `cond`（什么时候能做） | 太早动手时 | `failMsg` | `next` |
|---|---|---|---|---|---|
| 1 | **舀水** | 还没舀过 | 舀过了还想舀 | 缸已经轻了，再舀也是白舀。 | **挪缸** |
| 2 | **挪缸** | 舀过水了（缸轻了） | 缸还是满的 | 缸太沉，手指嵌进去一截，拔不出来。先倒掉些水会轻些。 | **舀水** |
| 3 | **掏灰** | 挪过缸了 | 缸还挡着 | 灰坑在缸后头，缸挡着，手伸不进去。 | **挪缸** |

⇒ **每一次失败都在指下一条路**，玩家不需要回头翻剧情。这就是 §3.4 那句话的实物。

🔴 **「掏灰」不是玩家动手**（`design/74` §辰时 明写：老汉侧着身子过去，**他**掏完灰，站直了拍手）。
所以它的定位是**触发位**，不是动作位：玩家点了它 ⇒ 老汉过去掏灰 ⇒ 播 `74` 「做完之后」那一段。
**我没有改 `74` 的剧本**，只把"谁动手"这件事说清楚 —— 否则玩家点了会以为是自己爬进灰坑。

#### （二）点亮是接力的，不是三个一起亮

§5.3 定的是「房间描写里可交互名词 ≤ 2 个（推荐 1）」。三件同处一室，**不能有三个亮着的词**：

| 时点 | 亮着的词 | 为什么 |
|---|---|---|
| 刚进茶摊 | **缸** | 只亮一个。它是挡路的那一个，也是玩家第一个会伸手的 |
| 舀完水 | **缸** | 还是它。现在推得动了 —— 词没变，话变了 |
| 挪完缸 | **灶膛** | 缸灭（`once` 用掉），灶膛亮。**接力棒交出去** |
| 掏完灰 | 全灭 | 房间永久追加「墙根有一片水渍，怎么也干不了。」 |

⇒ `瓢` **全程不亮**（`inDesc: false`）。它只在点「缸」展开的提示行里出现 ——
它是一条中间步骤，不是玩家会对着发呆的东西。

拿去跑 `questKeyword`（`commands.js:5650-5661`）才发现 ——
它对 `full='听书'` 的匹配是 `full.includes(k)`，`keywords=['说书']`，**两边都不包含 ⇒ 匹配不上**。
玩家照着提示敲「听书」，得到的是「『听书』是什么指令？」。**我自己的样例违反了我自己的 §6.5 铁律。**

⇒ 所以 `say` 的取值规则被钉死成一条机械可验证的断言（§8.2）：

```
say === a.cmd   ||   (a.keywords || []).includes(say)
```

⇒ 上面五条的 `say` 全部落在各自的 `keywords` 里，玩家敲了就能成。

### 7.2.1 🔴 扫描发现：256 条 `cmd` 里有 96 条（38%）根本不能提示给玩家

我原稿假设"提示里的指令名照抄 `cmd` 就行"。**把 256 条 `cmd` 全扫一遍之后，这个假设是错的。**

| `cmd` 形态 | 条数 | 例 | 照抄会变成 |
|---|---|---|---|

### 8.2.1 🔴 `say` 的取法（机械执行，不用手写 96 条）

我第一版的口径是"手写 96 条 `say`"，还画了一张按 `cmd` 形态套模板的表。**那张表是错的，删了。**
正确做法是**从 `keywords` 里挑** —— 因为 `say` 必须满足「玩家敲了能成」，而 `questKeyword` 的匹配口径
（`commands.js:5653-5661`）本来就认 `keywords`：

```js
if (ac === full || ac === cmd) return true;
if (full && ac.startsWith(full)) return true;
if ((a.keywords || []).some(k => k && (full.includes(k) || k.includes(full)))) return true;
```

⇒ **`say` 的三步取法：**

| 步 | 规则 | 命中条数 |
|---|---|---|
| 1 | `cmd` 本身就是纯中文（**词间允许空格**）且 ≤6 字 ⇒ `say = cmd`（不写） | **186 / 256** |
| 2 | 否则 ⇒ 从 `a.keywords` 里挑第一条满足「纯中文 / ≥2 字 / ≤6 字 / 不在 PANEL_CMDS / 不撞已注册指令 / 不以『看+别名』开头」的 | **52 / 256** |
| 3 | 挑不到 ⇒ **补一条 keyword，再从新 keywords 挑** | **18 / 256** |
| 4 | 🔴 **不许手写 `say`**（唯一例外见下） | **5** |

### 8.2.1-bis 🔴 第 3 步为什么是"补 keyword"而不是"手写 say"（主理人 2026-10-13 口径）

> **一旦开了"手写 say"这个口子，将来就会有第二条第三条，而手写的 say 最容易敲不动 ——
> 正是 §6.5 那条铁律要防的。**

⇒ **判据不变：`say` 必须落在 `keywords` 里**（`say === cmd || keywords.includes(say)`）。
挑不到就**改数据**（补 keyword），**不是放宽判据**。手写是例外，不是规则。

**本次 18 条补 keyword 的实测结果**（落盘 `tools/_out_say_keywords.tsv`）：

| 成因 | 条数 | 补的词 |
|---|---|---|
| 原 keywords 全是单字（`井`/`池`/`江`/`溪`/`水`/`稻`/`麦`/`摘`/`书`/`戏`） | **13** | 喝水 ×8（8 处水域的 `drink`）、看书、看戏、割稻、摘菜、割麦 |
| 原 keywords 两条都已注册（`赎身`/`脱籍`） | **5** | 赎出来（5 家青楼 `redeem`） |

⇒ **单字 say 从 13 降到 0。** 全部补的词都已验证：未注册 / 不撞 PANEL_CMDS / 不以「看+别名」开头 / ≤6 字。

⚠️ **13 条里那 8 条水域为什么不各写各的（`喝水` 一统）**：
八处都是 `cmd="drink"`、keywords 里都含「水」，提示句写「心里默念「喝水」」最像话；
按地点分写成「饮江水」「饮溪水」反而没人这么说话。**同类动作统一一个词，是提示系统的定律。**

**🔴 实测结论：96 / 96 条全部能从现有 `keywords` 里挑到 `say`，零条需要手写 keyword。**
（我把全部 256 条跑了一遍，见 §7.2 的五个样例。）

⇒ **批 0 的工作量从"手写 96 条"变成"脚本生成 96 条 + 人工过一遍挑词"。**

**挑词时的优先级**（同一条有多个候选时）：

| 优先级 | 规则 | 例：`keywords=["井","水井","打水"]` |
|---|---|---|
| 1 | 动词味的优先于名词味的 | 挑「打水」，不挑「井」 |
| 2 | 长的优先于单字的 | 「抓药」>「药」；「击鼓」>「鼓」 |
| 3 | 撞 PANEL_CMDS 的跳过 | — |
| 4 | 以「看」开头的跳过（§6.4） | — |

### 8.2.2 🔴 `say` 的守卫（一条断言就够了）

```js
// 对全部 256 条 action：
assert(say === a.cmd || (a.keywords || []).includes(say));
```

**为什么这条断言必须写进守卫**：`say` 是"说给人听的指令"。
如果它既不等于 `cmd`、又不在 `keywords` 里，**玩家照着提示敲下去，得到的是「『XX』是什么指令？」** ——
这正是 §6.5 那条铁律要防的事，而且**是我自己第一版样例踩到的坑**（§7.2）。

### 8.2.3 🔴 `next` 的守卫（比 `say` 的守卫多一条，因为它跨 action）

```js
// 对每一条写了 next 的 action a：
const target = (room.actions || []).find(x => x !== a && (x.cmd === a.next || x.say === a.next));
assert(target, `next「${a.next}」在本房间里找不到对应的 action`);
assert(a.next !== a.cmd, 'next 指回自己 —— 失败句会把玩家绕回原地');
```

**第一条断言为什么必须写**：`next` 是"你改敲这个"。
如果房间里根本没有那条 action，玩家照着敲 ⇒ **「『XX』是什么指令？」** ⇒ 又是 §6.5。
它比 `say` 更危险，因为 `say` 的落点在本条 action 的 `keywords` 里（自查即得），
**`next` 的落点在别的 action 上 —— 那条 action 哪天被删了，这边一声不响就废了。**

**第二条**：`next` 指回自己会形成一个"失败 → 再试 → 再失败"的死循环。
甲档三件的 `next` 是 舀水 ↹ 挪缸、掏灰 → 挪缸，**没有一条指回自己**（§7.1.1 那张表可核）。

**生成外壳的那两行（给寇豆码，`commands.js:5666` 就地改）**：

```js
if (a.cond && !evalCond(a.cond, ctx)) {
  const lines = a.failMsg
    ? [{ kind: 'warn', text: a.failMsg }]
    : [{ kind: 'warn', text: '现在做不了这个。' }];
  if (a.next) lines.push({ kind: 'hint', text: `心里默念「${a.next}」` });
  return lines;
}
```

`kind: 'hint'` 前端已有渲染（全库 178 处），不用新增样式 ——
**但这一行到底该多暗，归甄塑之**：它比 `warn` 轻（不该像报错），又不能暗到看不见。

### 8.3 🔴 两本账：`tutorialFlags` 与 `hintSeen` 必须分开

```
p.tutorialFlags[...]        ← 内置指令（look/get/talk/…），engine.js:1975 markTutorial 自动记
p.hintSeen[roomId|cmd]      ← 房间自定义指令（挪缸/舀水/掏灰/…），本次新增
```

**为什么不能合并成一本：**

1. `flagForCommand` / `FLAG_BY_CANON`（`tutorial.js:173-228`）认的是**内置指令的规范名**。
   「挪缸」这种房间自定义 cmd 根本不在表里 ⇒ 塞进去**永远点不亮** ⇒ L3 永远关不掉 ⇒ 变成一直弹的噪音。
2. `tutorialFlags` 的键是**指令名**，`hintSeen` 的键是 **房间 + 指令**（`commands.js:5487` 的 `actionLimit` 已经是这个口径：`(p.room||'') + '|' + (a.cmd||'')`）。
   同一个 `cmd`（比如「打坐」）在不同房间是**不同的事** ⇒ 必须带房间。
3. `tutorialFlags` 有白名单校验（`engine.js:1990-2001`），往里塞自定义键会被拦。

⇒ **给寇豆码：`hintSeen` 独立成一本账，别试图并进 `tutorialFlags`。**
