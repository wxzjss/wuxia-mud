### 1.3 🔴 阻塞项：`拜访`（visitHouse）能脱战，且自报结论与实测相反

**自报原文**（`13-owner-bug-fix-report.md:82-85`）：

> **`拜访`（visitHouse，上门拜访）→ 战斗中不产生位移。**
> 测试断言「战斗中拜访不产生位移」，成立。……**这是有意的**

**实测结论：战斗中拜访会真实位移，且`world.battle` 不会清除 —— 玩家可以带着战斗跑到别人家里。**

**复现步骤（可原样跑）**：

```js
const {GameEngine} = require('./game/src/core/engine.js');
const social = require('./game/src/core/social.js');
const e = new GameEngine({seed:20261008}); e.boot();
e.newGame({name:'验收', gender:'male', birth:'wuxue'});
const w = e.world, p = w.player;

// 1) 正常社交攒好感（不是作弊，改的是真实社交 API）
const target = w.allNpcs().find(n => String(n.def?.home||'') === 'house:' + n.defId);
social.addFavor(w, target, 40, '正常送礼/交谈');   // 初始 -2 → 38

// 2) 进战斗
let f=null;
for (const rid of Object.keys(w.data.rooms)) {
  const ns = w.npcsIncludingTemplates(rid).filter(n=>n.isNpc&&n.def&&n.def.hostile);
  if (ns.length) { f = {rid, npc:ns[0]}; break; }
}
w.movePlayerTo(p, f.rid);
w.startCombat(p, f.npc);            // 战斗开始

// 3) 战斗中拜访
const before = p.room;
e.exec('拜访 ' + target.name);
console.log('位移了?', before !== p.room);   // → true
console.log('现在在', w.getRoom(p.room).name); // → 范清家·堂屋
console.log('battle 仍悬空?', !!w.battle);     // → true
```

**实测输出**：

```
目标 NPC: 范清 | 初始 favor= -2
正常互动后 favor= 38 (门槛 30)
战斗中，我在 血刀门·前庭
拜访输出: 范清见你上门，眉头一动，末了让开身：「既是熟人，进来坐罢。」…
位移了? ✘ 是 → 现在在 范清家·堂屋
battle 仍悬空? true
```

**为什么这不是「理论漏洞」而是真实可利用**：

- 门槛只有 `favor >= 30`（`world.js:507canVisitHouse` 第��行），**正常送礼/交谈两三次就能到**。我用真实 `social.addFavor` 从 -2 攒到 38，全程合法。
- 位移后 **`world.battle` 仍非空**：玩家人已经在范清家，战斗却还挂着，敌人还留在血刀门。这是个**状态撕裂** —— 比单纯能走路更糟。
- 后果：玩家可借拜访无限脱战（每次战斗 → 拜访 → 战斗悬空 → 再拜访），**若配合「拜访完再 walk 回来」就彻底逃掉战斗**。这正是主人在 B5 里要消灭的行为（「能一路走回客栈」）。

**⚠️ 他的测试为什么是假绿（这是本次验收最关键的发现）**：

`tools/smoke-owner-bugs.js:203` 写的是：

```js
try { r = e.exec('拜访'); } catch (err) { threw = err.message; }
ok('B5-8 战斗中拜访不产生位移', p.room === before, ...);
```

**`e.exec('拜访')` 没有带参数**。实测输出是 `["你想拜访谁？"]` —— 在 `commands.js:957` 就return 了，**根本没走到 `visitHouse`、没碰到 `movePlayerTo`**。所以 `p.room === before` 必然成立，**这条断言在任何实现下都会通过，是典型的假绿**。

这条断言要真正有效，必须写成 `e.exec('拜访 ' + 具体NPC名)`，并先把好感喂到门槛以上。

**建议修法（很小，不扩大范围）**：

在 `commands.js` 的 `拜访` handler 里，进入 `visitHouse` **之前**加与 `doMove` 同源的战斗态门禁：

```js
reg(['拜访','造访','登门','上门'], (ctx, args) => {
  const w = ctx.world, p = ctx.player;
  if (w.battle) return { lines: [{ kind:'warn', text: COMBAT_MOVE_HINT }] };
  if (!args.length) return { lines: [{ kind:'warn', text: '你想拜访谁？' }] };
  ...
```

复用已有的 `COMBAT_MOVE_HINT` 常量，**零新增文案、零新增概念**。这样「拜访」与其他位移路径行为一致，`doMove` 那句「所有玩家自主位移都收敛于此」的断言也才真正成立。

> 附：`modapi` 的 `teleport`/`warp` 我同意**有意不拦**（属mod 作者的能力，不是普通玩家位移，锁它会砸掉 mod 玩法）。但建议在报告里把措辞从「传送有意不拦」改成「**mod 自定义传送指令**有意不拦」，避免主人误以为游戏内还有个传送按钮能脱战。

**关键事实：这 7 条 action 在 `50_map.json` 里根本没有 `effects` 字段**（34 条多词 action 里只有 1 条有 effects）。

- 修复前：这些 action 被静默吞掉 → 玩家看到「「listen」是什么指令？」

**这不阻塞验收**（代码侧一致性已达成：渲染什么、判定就是什么），但**属于主人应知道的内容缺口**。

### 9.8.2 B8 画像：`speciesOf()` 模板够不够铺 300 个 NPC？

**结论：机制够，判别规则远远不够。**

机制本身（注入 + speciesMoves + pickSkill 优先 + 不改 JSON）**设计得不错**，值得复用；但它的「判别层」目前是个**只能覆盖 2 个物种的玩具规则表**：

```

**实测判别力缺口**：
```
mob_crane | 丹顶鹤      => speciesOf: null   ← 规则表里没有这类，静默退回拳脚
mob_rat   | 巨鼠        => speciesOf: null   ← 同上

npc_snake_blade | 蛇婆婆 => speciesOf: snake  ← 误判（人是蛇）

铺 300 个 NPC 时会同时踩两类坑：

- **误**：任何名字/描述里带物种关键词的**人物**被误挂招式，正如已发生的蓝凤凰。

**建议**：
1. **铺开前先做判别层**：给 `SPECIES_RULES` 建立「动物 / 人物」的类型判据（而非靠关键词猜），或干脆**全面转显式声明**——300 个 NPC 本来就要逐个写画像，顺手写 `species` 字段最可靠，也让数据可审计。**我倾向这条：显式声明 + 全量遍历断言「人物模板永不带 speciesMoves」。**

w.rng.chance = () => true; w.rng.pick = arr => arr[0];

**它调的是 `rng.next()`，不是 `rng.chance()`。** 所以覆盖 `rng.chance` 对这条路径**完全无效** —— `rng.pick` 那个覆盖是有效的，但「必触发」那个覆盖是空的。

## 10.8 B7 官差不参与性格分流 —— 是有意还是疏漏？

### 实测（我独立跑，不是引述）

`witnessTree()` 的 `official` 分支排在性格判断**之前**。我强制给三种 official tag 的模板**逐一注入 9 种性格**（qienuo / xiayi / haoshuang / lengmo / baozhao / wenwan / mune / youhua / yinzhi），跑 `witnessTree`：

| tag | 模板 | 9 种性格产出 |
|---|---|---|
| `official` | npcv_017 莫时 | **1 种** |
| `constable` | npcv_016 戴青 | **1 种** |
| `escort` | npcv_015 滕逢春 | **1 种** |

台词全部是：`X厉喝一声拔刀：「光天化日持械行凶！山贼，你还不放下兵器！」`

**确认：性格分流对官差完全不生效。**（`escort` 也在 official 三档里，这一条尤其值得注意 —— 护镖/ escort 角色被归进了官府分支。）

### 我的判断：**更像有意，但注释没写明，且 escort 归档存疑**

**支持「有意」的证据**（代码逻辑自洽，不是笔误）：

- 官差分支的两条文案都是**功能性**的：「制止凶手」和「通缉凶手」，
  且代码注释明确写了「玩家是受害者 → 官差**制止凶手**，绝不能给受害者记通缉，
  否则玩家挨打反而被通缉，是彻头彻尾的反向效果」。
- 也就是说这个分支的**存在目的就是修一个 bug**（受害者被误记通缉），优先级高于性格表现。
- 性格分流的其余分支（怯懦逃走 / 侠义助战）都带**行为副作用**（`fleeNpc` / 加入 `battle.attackers`）。
  官差如果参与分流，一个 `qienuo` 的官差会「连滚带爬逃走」，一个 `xiayi` 的官差会「挺身加入战团」——
  **官差逃跑在武侠设定上说不通**，作者把它挡在外面是有道理的。

**支持「疏漏」的证据**：

- `escort`（护镖/随行）被归进 `official` 三档，语义上 escort 不是官府，是江湖护送。
  一个 escort 角色（`滕逢春` 等 9 个模板）打出「厉喝：光天化日持械行凶」的**官府口吻**，这在设定上是别扭的。
- 全仓共 **30 个模板**落在 official/constable/escort 三档（escort 9、constable 9、official 11，另有 `depot_master:official`、`bureau_clerk:official`）。escort 那一档占 1/3，量不小。

### 批3 的明确建议（三条，按优先级）

1. **保留 `official` / `constable` 不参与性格分流，但把 `escort` 从这三档里拿掉。**
   `escort` 语义上是江湖护送（镖师/随行），不是官差。让它走性格分流：
   侠义 escort 会「挺身加入战团」（合理），怯懦 escort 会逃走（也合理）。
   这是**一处纯配置修正**（`witnessTree` 里 `official` 的判定数组去掉 `'escort'`），风险极低。
2. **在 `witnessTree()` 的 `official` 分支上补一行注释**：
   「官差不参与性格分流 —— 官府职责优先于性格，且官差不应逃跑/加入江湖械斗。」
   把「有意」写进代码，避免下一轮又有人当疏漏改。
3. **补一条断言锁住这个决定**：断言 `official` / `constable` tag 的 NPC 在 9 种性格下台词**恒为 1 种**，
   并显式注明「这是刻意的」。这样将来谁要改性格分流，红灯会告诉他「你得先想清楚官差能不能逃跑」。

## 10.9 B8 判别层扩充方案评估

### 当前基础（我实测）

| 事实 | 数值 |
|---|---|
| 全仓 NPC 模板 | 333 |
| `mob_` 前缀模板 | **10** |
| `animal_` 前缀模板 | **0** |
| 已显式写 `species` 的模板 | **5**（全是 `mob_*`，由 `applySpeciesMoves` 运行时补写，数据文件里没写） |
| `SPECIES_RULES` 规则条数 | 2（snake / beast） |
| `SPECIES_MOVES` 物种数 | 2（snake 3 招 / beast 3 招） |

### 「锚定 id 规则表」够不够铺 300 个 NPC？

**我的评估：够用，但需要配套一条约束，否则 B8 铺开时会退化成第二套关键词表。**

**够用的理由**：

1. **判别层是纯查表，O(1) 扩展**。加一个物种 = 往 `SPECIES_MOVES` 加一组招式 + 往 `SPECIES_RULES` 加一条 id 列表。判别逻辑本身（`speciesOf`）一行都不用改 —— 这是当前设计最好的地方。
2. **两种入口并存，覆盖两种 authoring 风格**：
   - ① 显式 `def.species = 'snake'`（数据里写）→ B8 的 300 份 NPC 画像**逐个写这条最准**，一条 id 正则都不用加。
   - ②锚定 id 规则表 → 适合**成组的同类**（比如一次性加 20 匹狼，只需 `^mob_wolf` 一条）。
   工程给的建议是「新增物种要往 `SPECIES_RULES` 加锚定 id 并补招式表」—— **这个建议本身不完整**，因为它只说了入口②。**批 3 应明确：入口① 才是 300 份画像的主路径。**
3. **数量上完全够**：现在 5 个动物用了 2 条规则。铺 300 个 NPC，假设其中 15% 是动物（约 45 个），按每个物种 3~8 个模板算，需要 **6~15 条规则 + 5~10 组招式**。这个量级对一张人可读的表来说完全可控。
4. **可审计**：「谁被挂了物种招式」在 `SPECIES_RULES` 里一目了然，比任何正则面都强。

**必须配套的约束（否则会退化）**：

- ⚠️ **规则表会诱使人把 id 写成宽前缀**。现在只有 10 个 `mob_` 模板，所以 `^mob_wolf$` 和 `^mob_wolf` 效果一样；一旦铺到 300 个，**写 `^mob_` 前缀就会重新变成关键词面**，`mob_bandit` 那种人物会命中。
- **守卫 7 会兜住这个**（白名单里现在只有 5 个人物；`^mob_` 写宽后山贼会判出物种 → 不在白名单 → 立刻红）。所以**只要守卫 7 一直在，这个退化就会被抓到**。这是当前设计最有价值的一处：它把「规则表写宽」这个诱惑变成了有报警的。

**对工程方案的评估结论**：

- 「往 `SPECIES_RULES` 加锚定 id 并补招式表」→ **正确但不完整**，需补上入口① 作为主路径。
- 建议补一条**新增物种的自检清单**（批 3）：
  1. 往 `SPECIES_MOVES` 加招式（`type` 必须是「拳」类，不能是剑/刀/棍/鞭/暗器 —— 否则动物会吃「手中无兵刃」惩罚，`combat.js` 的 `WEAPON_REQUIRED` 会硬套武侠兵器规则到没手的蛇身上）；
  2. 招式数 **≥ 2**（只1 招在观感上与原 bug 无区别）；
  3. 往 `SPECIES_RULES` 加**全名锚定**的 id 列表（或给模板显式写 `def.species`）；
  4. 新模板若不是动物而是人物 → 加进 `HUMAN_MOB_WHITELIST` 并确认它确实是人；
  5. 跑 `smoke-owner-bugs`，守卫 1~7 必须全绿。
- **一条我要额外提的风险**：`isAnimalId` 的闸门只认 `mob_` / `animal_` 两个前缀。**当前 `animal_` 前缀模板数为 0** ——
  说明这个前缀是**为未来预留的、目前完全未使用**的。若批 3 铺开时不统一命名约定（比如有人用 `beast_` / `wild_` 前缀），闸门会把这些动物**静默判不出物种**，而守卫 7 的白名单里没有它们 → **会红**（这是好事）。
  但更危险的情形是：有人为了「让守卫 7 变绿」而把新动物**塞进白名单**。守卫 7 的第二条（白名单里的模板必须确实是人，含 `looksBeast` 排除）能拦住一部分，但拦不住「起了个不像动物 id 的名字」。
  **建议批 3：命名约定写进注释**（`mob_` = 战斗用生物 / 敌对单位，`animal_` = 中立野兽），并在 `applySpeciesMoves` 启动时打一条 modLog 统计「有多少 `mob_` 模板判不出物种」，让可疑数字出现在日志里而不是只出现在断言里。
