## 卷首 · 三条事实更正：现在的战斗到底是不是"一指令一手"

**第一条：是。战斗本来就是一指令一手，F.2 ① 的"换驱动"不要做了。**

`world.combatStep(userAction)`（`world.js:2666`）是战斗的唯一入口。四条玩家分支都是干净的"玩家一手 → 敌人一手"：

| 玩家指令                   | 位置                        | 走法                                                                          |
| ---------------------- | ------------------------- | --------------------------------------------------------------------------- |
| `defend / 防御 / 招架 / 守` | `commands.js:3429`        | `combatStep({type:'defend'})` → 置 `battle.guardTurns=1` → `stepEnemyOnly()` |
| `绝招 <武学>`              | `commands.js:2837 / 2843` | `combatStep({type:'skill'})` → `oneAttack()` 一次 → `stepEnemyOnly()`         |
| `flee / 逃跑`            | `commands.js:3435`        | 逃跑判定 → 失败则 `stepEnemyOnly()`                                                |
| 战斗中用物品                 | `world.js:2777`           | `useItem()` → `stepEnemyOnly()`                                             |

`stepEnemyOnly()`（`world.js:2794`）就是"敌人随后出手一次"。**"防御"这种"放弃这一手换减伤"的指令存在，本身就证明一手已经是一个决策单位——架构总监这个判断是对的。**

⇒ **F.2 ① 从"换驱动"降级为"不用改"**，F 节只做"换演出"（本任务）与"修一个调用"（下条）。**工作量小一个数量级。**

**第二条：但有一个真 bug，比我设计案 F.1 写的那条严重，而且是"敌人一回合打两次"。**

无参数的 `attack` —— 也就是战斗面板上那&#x4E2A;**「全力一击」按钮**（`commands.js:3348`，注释明写"交战中无参数 = 朝当前对手全力出手"）——走的是这一路：

```js
// world.js:2784-2786
const r = this.combat.step(this.battle);   // ← 让全场单位各打一次（含敌人）
let lines = r.lines;
lines = this.stepEnemyOnly(lines, true);   // ← 敌人再打一次
```

而 `combat.step()`（`combat.js:106`）内部是**遍历双方所有单位**各出手一次（`combat.js:118-167`，`all` 由 attackers + defenders 合并，`for (const ent of all)` 逐个 `oneAttack`）。

> **一次点击 = 玩家出手 1 次，敌人出手 2 次。**

**第三条：`auto` 不是"一键打完"，它是把这个"敌人多打一次"的循环跑了 60 遍。**

`auto`（`commands.js:3441`）：`while (battle && !battle.over && guard++ < 60) combatStep()`。

所以我设计案 F.1 那句"玩家没出手就结束"**口径错了**。真实机制是：玩家每循环出手一次，敌人出手两次，循环最多 60 次 —— 玩家当然打不过，而且全程没有决策。**F.2 ① 的"把 auto 改名挂机"依然要做，但"改回合驱动"不做。**

## 任务一 · 战斗演出句库 v2（v1 已废，理由在 1.0）

### 1.0 先认这个病：v1 的「万能骨架」就是模板本身

> **主人原话（一字未改）**：「这几句话怎么感觉还是有一股ai味，比如：他这一掖落在你小臂，闷响。你衣服上留下一个灰手印。你这一顶落在他右肋，他的腮帮子先肿了。血是从嘴里出来的，牙磕的。他这一炮砸在你左肩。你听见肋上响，响完之后每喘一口气都像有人在里头拽。」

**这个判断我认，而且认得心服口服 —— 病根是我自己造的。**

v1 里我把所有动词槽统一成「{A}这一{V}落在{T}{P}」，理由我在 1.2 里写得很清楚：**「落」是唯一对全部近战动词成立的落点动词**。这个理由是真的。**但正因为它万能，它就必然成为最显眼的模板。** 我用一个"万能结构"换掉了"随机组合"，结果"万能结构"本身就是模板 —— 这是同一个病换了件衣服。

主人点出四条，我逐条复核并**量化**（不量化就只是"我觉得"）：

| 主人点的 | 我的复核（可验证的数字） |
|---|---|
| ① 结构太整齐 | v1 的 **160 条骨架全部走「这一{V}落在{P}」一个句法**。三句同形，读三遍必然闻到味 |
| ② 句句都要一个精妙观察 | v1 每句都在同一位置收一个"观察尾巴"（灰手印 / 牙磕的 / 像有人在里头拽）。**真人写打斗会允许糙句** |
| ③ 明喻密度高 | v1 明喻散在各档；v2 压到 **4 条 / 224 条 = 1.8%**，且只许出现在"声音式"这一种句式里 |
| ④ 缺极短句 | **v1 的 160 条骨架里最短 12 字，一句短句都没有**，骨架句长方差只有 **14.4** |

第 ④ 条我算完自己愣了一下：一个专门写打斗的句库，**一句短句都没有**。可真人写打斗一定有「他一拳打在脸上，血就下来了」这种不带观察、就停在那儿的句子。**不完美的句子才是人写的。**

> ⚠️ **最关键的一条（主人的原话）**：**「你的环形缓冲排除的是『骨架』，但如果所有骨架都是同一个句法结构，缓冲就没用 —— 要改的是骨架的多样性，不是数量。」**
> 这句话是对的，而且它不只对 v1 成立 —— **它是一条通用的检查规则**：*任何"防重复"机制，都防不住"结构层面的单调"。*

### 1.1 v2 的改法：把「句式」提成第一层

v1 是三层：动词 × 部位 × 程度。
**v2 是四层：句式 × 动词 × 部位 × 程度**，且**句式排第一**。

> **口径一句话**：不再输出"谁用哪招打中谁、掉多少血"，改为输出"谁的什么动作落在对方身上哪个部位、成了什么样" —— **并且每一句用什么句法说，也要换着来。**

**8 种句式（每种一条说明 + 一条真骨架）**：

| # | 句式 | 干什么用 | 真骨架举例 |
|---|---|---|---|
| 1 | **动作式 act** | 「这一{V}落在{P}」—— v1 的唯一骨架，**现在只占 1/8** | `{A}这一{V}落在{T}{P}，皮翻起来一小条。` |
| 2 | **结果式 result** | 不写怎么打的，只写身体后来成了什么样 | `{P}那块先白后红，摸上去是热的。` |
| 3 | **声音式 sound** | 只写声音。**全库唯一允许带明喻的句式** | `剑刃刮过去，声音又干又短。` |
| 4 | **连锁式 chain** | 身体连锁反应：撞到东西、退、坐下去 | `{T}身子一歪，扶住墙才站住。墙皮掉了一小块，掉在脚边。` |
| 5 | **糙句 plain** | **不带观察、不带比喻，就停在动作或结果上** | `{A}这一{V}落在{T}{P}。{T}没还手，先退了半步。` |
| 6 | **极短句 short** | 4–6 字，不带 {V} 不带 {P} | `骨头响了。` / `架住了。` / `见了点红。` |
| 7 | **延迟式 delay** | 疼或血来得晚，过一会儿才知道 | `{T}当下没觉出什么，过了一会儿血才渗出来，渗成一条细线。` |
| 8 | **器物式 thing** | 写兵器、衣裳、地面，**不写人** | `{Td}衣裳破了个口子，口子里露出来的还是好肉。` |

**四条硬规矩（对应主人那四条）**：

1. **8 种句式强制轮换** —— 每一档的 8 条骨架必须**各占一种句式**，一条不多一条不少。
2. **糙句占 2/8（plain + short）**，另有 act 里的一部分停在动作上、不收尾巴。**合计约七成的句子不带"观察尾巴"。**
3. **明喻只许出现在声音式**，每类一条，全库 4 条。
4. **必须有极短句** —— short 句式一律 4–6 字。

### 1.2 为什么动词也要动：不是所有动词都接得住「落」

v1 我只顾着让**骨架**统一，没检查**动词**接不接得住。v2 连读三场时这个问题自己浮出来了：

| 渲染出来的句子 | 为什么不成立 |
|---|---|
| 「这一**拖**砍进你咽喉」 | 拖是"拉"，不是"落"；后面再跟一个动词「砍进」 |
| 「这一**按**落在小腿」 | 按不住，也不落 |
| 「这一**挂**落在手肘」 | 挂是勾住，不是落下去 |
| 「这一**擒**落在你小臂」 | 擒是抓住，不落 |
| 「这一**推**落在后腰」 | 推是推出去，不是落下来 |

**刀类 14 个动词里有 4 个接不住（拖/按/挂/撬），拳类有 4 个接不住（擒/推/别/拧）。** 这就是"骨架换了还是有点别扭"的**真正病根** —— 骨架换了，动词还是接不上。

**改法：动词全部换成接得住本类句式的字。** 换完以后，四类各 14 个字，**全部能接「这一{V}落在{P}」**（暗器类接「手一{V}」），**跨类复用仍为 0**：

| 类 | 14 个动词 | 换掉了什么 |
|---|---|---|
| **剑** | 抹 点 绞 撩 崩 刺 穿 截 递 划 抽 扫 压 挑 | 削 划给刀了，换进「绞」 |
| **刀** | 劈 剁 斩 铲 捅 削 抡 拍 磕 顿 扎 砍 刮 砸 | 换掉 拖/按/挂/撬/背砍/夯，换进 铲/削/拍/顿/扎/砍/刮 |
| **拳** | 捣 掖 顶 靠 掴 抄 挫 炮 撞 轰 掀 夯 切 戳 | 换掉 擒/推/别/拧，换进 掴/轰/掀/夯 |
| **暗器** | 甩 抖 弹 掷 扬 扣 撒 抛 翻 脱 送 挥 掠 旋 | 未动（「手一＿」全部成立） |

### 1.3 两条缓冲：环形缓冲管"不撞同一条"，句式缓冲管"不撞同一个句法"

**这是 v2 的核心机械保证，也是主人那句批评的直接答案。**

| 缓冲 | 排除什么 | 保证什么 |
|---|---|---|
| **环形缓冲**（v1 就有） | 同一把钥匙下最近 **6 条**骨架 | 同一档位连续 6 次不出现同一条骨架 |
| **句式缓冲**（v2 新增） | 最近 **2 个**句式 | **连续两条不得同句式** —— 不管它们属于哪一类、哪一档 |

**为什么两条都要**：环形缓冲是按「类 + 档」分桶的，**它管不了跨桶**。v2 连读时抓到过真事：

> 第 27 场里「响声过后是麻，麻过之后才是疼」出现了两次 —— 一次来自剑类骨档，一次来自拳类骨档。**环形缓冲分桶存，两条都在各自的桶里合法，撞在一起就没人管。**

所以 v2 加了两条措施：

1. **句式缓冲跨桶生效**：`patHist` 只记最近 2 个句式，与类、档无关。
2. **跨桶撞句人工清零**：我扫了一遍全部 224 条骨架（主骨架 160 + 落空 32 + 被架住 32）的**跨骨架 ≥8 字共享串**，清出 **13 组**，全部改写。**现在这项是 0 组。**

### 1.4 为什么骨架是 160 条 + 落空/被架住各 32 条

v1 我按"4 类 × 5 档 × 3 条 = 60"交初稿，渲染一场 20 手的架出来，**同一条尾巴撞了两次**；扩到 160（每档 8 条）后，10 场实测 ≥12 字重复串全 0。**这个结论 v2 继续用，但理由变了** —— 每档 8 条不只是为了"够用"，是为了**让 8 条刚好各占一种句式**。

v2 还补了一处 v1 没做的事：**落空和被架住也要有骨架**。v1 里这两种情况各只有 3–4 条，连读时抓到过：

> 「你这一挫落空，拳头擦着那使刀的耳朵过去」在同一场里出现两次（第 02 场第 10 手和第 20 手）。

**落空 / 被架住现在各 4 类 × 8 条 = 32 条，8 条同样各占一种句式，缓冲规格与主骨架完全一致（排除最近 6）。**

### 1.5 四类的手感说明（这一刀和这一剑，打在身上为什么不一样）

| 类 | 手感说明（这条要能被程序员读出来，也要能被文案抄走） |
|---|---|
| **剑** | 剑走轻。它不砸，它划过去。中剑的人当下常没什么感觉，过一会儿才发现衣裳湿了一片 —— **剑伤的疼是慢的，是从凉开始的。** |
| **刀** | 刀走分量。它不划，它砍。中了刀当下就知道，因为骨头先响，响完了皮才开 —— **刀伤的疼是快的，是从里往外炸的。** |
| **拳** | 拳是贴着来的。要打到人先得够得着，所以拳伤总带着身体撞在一起的那一下：胸腔里的气被顶出去，鞋底在地上蹭。**拳不打远，它打近。** |
| **暗器** | 暗器来得没声，来之前没有先兆。它不像拳脚有起手，所以中了暗器的人第一反应常常是"什么东西"，第二反应才是疼。**暗器伤小，但伤口脏。** |

### 1.6 与引擎的接缝（只需三处，都很小）

| 位置 | 改动 |
|---|---|
| `combat.oneAttack()`（`combat.js:496-511`） | 结算完成后**不再自己拼那句模板**，改为返回 `{ style, hpRatio, crit, blocked, missed, dmg, aName, tName }` 交给渲染层。`text` 字段保留为兜底，句库取不到时还能用 |
| `ui.js` 战斗渲染处 | 调 `COMBAT_LINES.render(style, hpRatio, opts)` |
| `index.html` | 引一行 `<script src="js/combat-lines.js?v=2"></script>`（**独立文件，不参与首屏，可缓存**） |

**`style` 从哪来**：由武学数据补一个 `style` 字段（`sword / blade / fist / hidden`），取不到就按玩家当前兵刃类型兜底，再兜底用 `fist`。**这是 §B.4 武学合并时顺手补的字段，不额外开工。**

**`hpRatio` 从哪来**：`dmg / t.maxHp`，`oneAttack()` 里 `dmg` 和 `t.maxHp` 都已经在手边，**不需要新增任何计算**。

**数值模式怎么处理**：`opts.mode === 'numeric'` 时只在句尾补一个括号 `（-37）`，**正文不动**。开关放在设置里，默认关。**玩家打开数字，是因为他想算，不是因为他想看数字代替描述。**

### 1.7 这一版不做的事（说清楚边界）

| 不做 | 原因 |
|---|---|
| 不写"围观者/目击反应"句库 | 那是 C4，属于另一池子；本次只解决"招式落到身上"这一层 |
| 不给每个门派单独配动词 | 761 门武学按四类合并后，靠 `style` 字段区分就够了。**给 761 门各配一套动词是自杀** |
| 不做"连招描述"（如"青龙出水接白蛇吐信"） | 连招要先有连招系统。现在没有，写了也是空文 |
| 不处理内伤/中毒/点穴的表现 | 那是状态，不是打击。留给下一版的「状态层演出」 |

    var src = forceArr && forceArr.length ? forceArr : arr;
    var h = hist[key] || (hist[key] = []);
    var pool = src.filter(function (x) { return h.indexOf(x) < 0; });
    if (!pool.length) pool = src;
    var it = pool[Math.floor(Math.random() * pool.length)];

    patHist.push(it.p);

    return it;

    var P = pickNoRepeat(parts[tierKey], 'part_' + style, 2);

**四条自检入口（给验收的人）**

| 想验什么 | 怎么验 |
|---|---|
| 句式是不是真的轮换 | 每档 8 条骨架的 `p` 字段应互不相同：4 类 × 5 档 = 20 组，每组 8 个不同句式（实测 `{"act":20,...,"thing":20}`，各 20） |
| 连续两条会不会同句式 | 连渲 200 手，看相邻两条的 `p` 是否从不相同 |
| 跨桶会不会撞句 | 全库 224 条骨架两两比对 ≥8 字共享串，应为 **0 组**（我扫过了，见 §A） |
| 换文案会不会崩 | 只改 `frames` 里的 `t`；**`p` 字段不能删，删了句式缓冲就失效** |

### 1.10 暗器类专项修订（v2.1 · 2026-10-12）

#### 为什么要改（不是因为那 145 组）

主程序用更宽口径（占位符算 1 字、保留标点）扫出 145 组 ≥8 字共享串，**集中在暗器类**。但 145 这个数是**穷举语料口径**——同一条骨架被 14 个动词 × 14 个部位展开后，同一句在全库出现上百次，会被计成上百组。**环形缓冲是渲染层机制，按 class+tier 排除最近 6 条，它管的是"一场之内"，管不了"全库"。** 穷举语料里的重复清不掉，也不该清（清掉了等于把动词和部位这两个维度删掉）。

**真正该改的是我自己扫出来的另一件事，比 145 组严重得多**：

> **`{A}手一{V}` 在 hidden 里出现 15 次，在 sword / blade / fist 里出现 0 次。**

**第二条理由，是主程序举的那个例子本身**：

```

blood/act：{A}手一{V}，那东西扎进{Td}{P}。

重伤句是轻伤句**删掉一个尾巴**。这是反的——**伤得越重，句子应该多出点什么，不是少**。而且它让「观察」长在轻伤句上、重伤句反倒成了糙句，**严重程度与观察密度负相关**，正是主人闻出来的那个味的变体。

#### 顺手修掉的一条回归：`{T}的` 绕开了所有格保护（守卫 §5-2 抓到的）

`frames.fist` 里有一条 delay 骨架原本写的是：

```js
{ p: 'delay', t: '{A}这一{V}停在半路上。{T}的手已经等在那儿了。' }   // ← 错
```

**病**：`{T}` 是**名字原文**（如「那使刀的」），后面再硬编码一个「的」，就变成

> 「那使刀的」+「的」+「手」= **「那使刀的的手」**

而 `{Td}` 是**所有格占位符**，它自带保护（`poss()`：名字以 `的 / 你 / 他 / 她` 结尾时**不补「的」**）。
**写 `{T}的` 就是绕过了这道保护**——把 §1.6 那条规则架在空中。

**改法**：`{T}的手` → `{Td}手`

| 名字 | 改前 | 改后 |
|---|---|---|
| 那使刀的 | 「那使刀的的手」❌ | 「那使刀的**手**」✅ |
| 守山弟子 | 「守山弟子的手」✅ | 「守山弟子的手」✅ |
| 你 | 「你的手」 | 「你手」 |

| 重复标点（`。。` `，，` `、、`） | **0** ✅ |
| 叠字（`了了` `着着` `在在`） | **0** ✅ |

**全库只有这一处**：`{T}的` / `{A}的` 各扫一遍，`design/75` 与 `combat-lines.js` 里**就这一条**。改一处就干净了。

## 任务二 · 13 件深门手动件逐件脚本

### 2.0 先说一件架构上的事：痕迹写在哪儿（这一条决定下面 13 件怎么写）

设计案 §H-b 原写的是「房间描述永久改变，追加在描述之后，引擎增加 `room.marks`」。**这句话现在不能照着做了 —— 架构侧核出来了：`w.data.rooms` 是进程级共享模板，往 `w.data.rooms[X].marks` 里写一句话，会把一个人的水渍漏进所有存档。**

⇒ **下面 13 件里，每一件的「成功后留下的那句话」都写成一条独立句，字段一律是：**

```
p.roomNotes[roomId] = '……一句话……'      // 存档级，跟着玩家走
```

**为什么不挂在 `world` 上**：`world` 也是进程级对象。除非 `world.roomMarks` 再按玩家 id 开一层键（`world.roomMarks[playerId][roomId]`），否则它和 `w.data.rooms` 是同一个病。**多开一层键不如直接挂在玩家身上，且玩家侧字段天然随存档序列化，备份/回档不用额外处理。**

> ⚠️ **2026-10-12 改名：`p.marks` → `p.roomNotes`。** 我原来选的 `p.marks` **撞字段了**（team-lead 查实）：
> ```
> world.js:99   const marks = p.marks || [];
>               if (marks.indexOf('丧亲') >= 0) b -= 8;
>               if (marks.indexOf('新婚') >= 0 || marks.indexOf('得子') >= 0) b += 10;
> ```
> 它已经是**玩家的人生标记数组**（`'丧亲'` / `'新婚'` / `'得子'`…），喂给 `portraitMoodBias()` 算画像情绪偏移；`createPlayer` 里初始化为 `marks: seed.marks || []`。往它上面挂 `marks['huashan_siguoya']` 技术上能跑（数组也是对象），但**语义上两个东西挤一个字段** —— 跟这个项目"看起来能用，实际在埋雷"的老毛病是同一族。**下面 13 件全部用 `p.roomNotes`。**
>
> 另外一条悬案已结：`world.roomMarks` **全仓 grep 为空，字段根本不存在**。真要建也是新建，那就直接用玩家侧字段，不用再等技术侧确认。

**渲染位置**：房间固定描写 → 动态句（时辰/节气/天气）→ **痕迹句（`p.roomNotes[roomId]`，0–1 句）**。三段的顺序固定，痕迹句永远在最后，**因为它讲的是"你来过"。**

**每房只留一句**：`p.roomNotes[roomId]` 是**单值不是数组**。同一间房做了两件不同的事，后一句覆盖前一句。**这是有意的**：一个人对一间房的记忆，最后只剩一件事。

### 2.1 通用规格（13 件共用，写一次）

| 项             | 规定                                                                           |
| ------------- | ---------------------------------------------------------------------------- |
| **H1 多步**     | 每件 4–5 步。**顺序写死**，跳步直接判失败（不是"少做一步扣分"，是"这件事没发生过"）                             |
| **H2 身体成本**   | 每步消耗气力 1–5，或负重、或道具、或承担一点风险（见每件表格）。**没有一步是免费的**                               |
| **H3 环境参与**   | 天气 / 时辰 / 负重 / 状态至少三项插手，且**必须有一项是"让这件事变难"而不是"让这件事变容易"**                      |
| **H4 可失败可恢复** | 失败有具体文本，不致命，不损功力，不扣银钱。**失败三次**才锁，锁的时长每件不同（见 ⑤）                               |
| **H5 永久痕迹**   | 成功后写 `p.roomNotes[roomId]`；且**至少一个人会记得**（每件都配一句"下次见到他时会说的闲话"）                    |
| **不可跳过的输入**   | 每步都要玩家**输入一个动词**（拾 / 引 / 添 / 守……），**不出现"点一下确定"**                             |
| **文本量**       | 每件：分步表 4–5 行 ×（成功 + 失败）两句 + 环境表 3–5 行 + marks 一句 + 记得那人的一句。**这是 13 件能被写完的量** |

**共用失败兜底**（三句，随机取一，只在判定失败且无专属文本时用）：

> 你的手先不听话了。这件事今天做不成。  
> 你退开一步。东西还在原处。  
> 你试到一半停住了。再试下去要坏。

### B. 关于「整库 25/100」这句实话（v2 仍然成立，别被这个数误导）

整库穷举的**困惑度是 100**，因为检测器数的是「≥12 字重复串的**处数**」——**它是个计数，不是比例。文本越长，处数必然越多。** 任何组合式句库（固定骨架 × 随机槽位）在长样本下都会撞到这个天花板 —— **这不是 AI 味，这是"句库"这种形态的固有属性。**

**所以正确的指标是单场，不是整库**：

| | v2 句库 | v1 句库 | 现有模板 |
|---|---|---|---|
| 单场（一场架）均值 | **1.7** | 7.4 | —— |
| 单场 >10 的比例 | **0/30** | 7/30 | —— |
| 整库 300 句 / 穷举 | 25 | 25 | 44 |
| 句长均匀度 | 5（方差 ≈ 48） | 5（方差 ≈ 41） | **74**（方差 6.44） |

**顺带说一件事：检测器抓的是"重复"，不是"写得烂"。**
现有模板的**词汇分布、标点、逻辑三维全是 0** —— 它拿 44 分只因为句长整齐 + 复读。**也就是说，一个"句句一模一样"的模板在这套指标下只算 44 分；写得再"像人"也没用，因为它根本不产生新句子。**

**这一条在 v2 上更值得说一遍**：v2 拿 1.7 分、v1 拿 7.4 分，**差的是重复，不是文笔**。主人的原话是「有一股 AI 味」——**这个"味"是结构问题（句句同形），检测器恰好也把结构同形的后果（重复 + 句长整齐）记成了分数**，所以这次分数和人的判断是同向的。**但下次如果分数低而人还是觉得有味道不对，以人为准。** 我把这句写下来，是因为它会误导后面做验收的人：**分数只能用来比 A/B，不能用来判好坏。**
