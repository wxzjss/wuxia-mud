## 第一章 · 缺陷分级

### 1.1 分级判据（先立规矩，再谈分级）

判据不凭「感觉严重」，只落到三个可观测的问题上。**三条全中 = S1；中两条 = S2；中一条 = S3；全不中 = S4。**

| 编号 | 判据问句 | 为什么用这条 |
|---|---|---|
| **J1 阻断** | 玩家**能不能继续玩**？是否出现「无法推进主线 / 卡死 / 存档读不出来」？ | 唯一真正伤到留存的一类。B5（战斗中能走回客栈）在此列：它让整个战斗系统可被绕过。 |
| **J2 毁档** | 是否**破坏存档完整性**（存档丢失 / 读档后状态错乱 / 覆盖到别的档）？ | 毁档不可逆、成本最高，宁可误判为高。 |
| **J3 观感** | 玩家会不会**以为功能坏了 / 世界是空的**？ | 主人亲报的 8 条里有 5 条落在这里。B4/B6/B7 属此类：功能没崩，但玩家读到的是「这游戏没做完」。 |

**严重度定义**

| 级别 | 定义 | 处置时限 |
|---|---|---|
| **S1 阻断** | 玩家无法继续玩，或会毁档。 | 本批次必修，不接受「下个版本」。 |
| **S2 严重** | 玩家能玩，但核心系统被绕过 / 关键功能静默失效。 | 本批次或紧邻批次必修。 |
| **S3 中等** | 不阻断，但玩家会明确感到「这是个空壳 / 功能坏了」。 | 下一批必修。 |
| **S4 轻微** | 打磨项，不影响可玩性与信任感。 | 有余力再做。 |

**修正因子**（命中则升一级，降级需在表里写明理由）

- **M1 可复现性**：确定性复现（每次必现）比偶发（依赖随机种子）**升一级**；只在特定机型出现（触屏 / iOS Safari）**降半级**（影响面小但不可在桌面复现，需专项验）。
- **M2 掩盖关系**：一条 bug 会把另一条的体感吃掉，导致主人误判优先级。**被掩盖的那条按它的真实严重度记，不按主人感知的严重度记**（详见 1.3）。
- **M3 静默失败**：不报错、不提示、直接返回空/假（玩家以为是自己操作错）**升一级**。这是最恶劣的一类体验。

### 1.3 掩盖关系分析（M2 因子）——本节是本次分级最关键的判断

**B1 掩盖 B2，且 B2 的真实成本被 B1 放大了。**

实读证据：
- `engine.js:938-948` `listSaves()` 把 `saves/` 目录下**所有** `.json` 一律列出，**无任何 uid / 来源过滤**，最后按 `savedAt` 降序排。
- 实测 `saves/` 目录三个文件：`save_2026-10-09T15-51-38.json`（玩家「试剑」）、`save_2026-10-09-09T15-52-38.json`（玩家「试剑」）、**`test_slot.json`（玩家「测试侠客」）**。
- 实测 `savedAt`：`test_slot.json` = `1791564295040`，**比两个真存档都新**。

推论：**如果只修 B2 不修 B1，「继续游戏」会自动把玩家送进「测试侠客」那一档** —— 这是把一个 S3 观感 bug 升级成一个 S2 毁档级事故。

因此：
1. **B2 单独修是危险的**，必须与 B1 同批或在其后。
2. **反过来说，B1 其实是 B2 的前置**：B1 的验收标准（`12-owner-bug-list.md:33`）只写了「测试档要么删干净要么不可见」，**不够**。真正的验收应追加一条：**列表里不得出现任何非当前玩家所属的档**，并且**排序不能被测试档污染**。

> 建议工程负责人顺手把这条判据补进 B1 的验收标准里 —— 这不是加需求，这是把「删一个文件」升级为「修一条会污染排序的链路」。

**B4 掩盖 B5 的体感。**

主人报 B4 时正在打山贼，同时也在报 B5。同一次遭遇里两个 bug 叠在一起：
- 战斗面板上「全力一击 / 防御」两个键点了没反应 → 玩家以为战斗 UI 坏了；
- 同时又能走动 → 玩家以为自己操作没生效，只是「战斗 UI 有点问题」。

结果：**主人把 B5 的体感归因到了 B4**（B5 在台账里写的是「高」，B4 写的是「中」）。本表按真实判据把 **B5 提到 S1、B4 降到 S2**，理由是：
- B5 命中 J1（能绕过整个战斗系统）+ J3（世界规则不成立），M3 命中（无任何提示，走就走了）。
- B4 命中 J3，但**不命中 J1/J2**（战斗仍可通过「普通攻击 / 逃跑」完成），且 M1 降级（桌面端点按键盘可达同功能，非触屏专属）。

### 1.4 B4 的实读结论（给工程负责人的定向情报）

我在读代码时定位到 B4 的根因，**建议按「删僵尸按钮 + 补一个真按钮」处理，而不是仅接线**：

- `ui.js:2220-2226` 战斗中快捷栏渲染为：`普通攻击→auto`、`全力一击→attack`、`防御→defend`、`逃跑→flee`。
- **`defend` 在 `commands.js` 里全仓没有任何 `reg()` 注册** → 点下去后端返回「未知指令」，按钮静默无效。**这是「僵尸按钮」，不是没绑事件。**
- **`attack` 有注册，但注册在 `kill` 上**（`commands.js:1706`：`reg(['kill','fight','attack','杀','攻击','打'], ...)`），它需要**一个目标参数**。在战斗中点「全力一击」不传参 → 走到 `commands.js:1708` 返回「你想攻击谁？」。**所以它绑定是绑了，但绑错了指令**，属于更隐蔽的一类僵尸按钮。

> 结论：**按主人授权「如果废弃了可以删了」处理** —— 建议删掉这两颗按钮，或把 `attack` 改成正确的战斗动作指令、`defend` 补一个真实现。**不要只修事件绑定**，那只会把「静默无效」变成「点了却说『你想攻击谁？』」。

### 1.5 B7 的实读结论

**好消息：机制已经有一半了，缺的是钩子，不是从零做。**

- `world.js:951-994` `witnessReaction(victim)` 已实现完整反应树：官府目击（通缉+1）/ 侠义有武力（挺身制止）/ 怯懦（**调用 `fleeNpc` 真的逃走**）/ 有武力（警惕）/ 无武力（惊呼）。
- `world.js:1048` `fleeNpc(npc)` 已实现（挪到相邻出口，无出口则 despawn）。
- `personality.js:10-20` 九种性格已含 `qienuo 怯懦`、`xiayi 侠义`，`world.js:974/978` 已按性格分流。

**缺口精确定位：**`witnessReaction` 只在 `onNpcDown`（`world.js:838`）与 `onNpcKilled`（`world.js:907`）里被调用 —— **也就是只在「NPC 被玩家打倒/打死」时触发**。
而 `startCombat`（`world.js:1556-1573`）里 **`this.emit('combatstart', ...)` 发出去了，但全仓没有任何监听者**（我 grep 过 `combatstart`，只有两处 `emit`，零处 `on`）。

所以 B7 的根因是一句话：**「战斗开始」这个事件没人听。** 修法方向是给 `combatstart` 接上目击反应（玩家是挨打的一方时，反应树应该反过来：仗义的上前帮忙、怯懦的逃跑、看客惊呼）。这与现有的 `witnessReaction` 是**镜像**逻辑，可以复用大部分判断，建议抽成共用函数而不是复制一份。

### 1.6 关于 B3 的批次建议（已获主人采纳）

主人钦定 B8「等画像后再做」，本表完全尊重。但 **B3 与 B8 虽同源，实际可以提前**：B8 是「给三百个 NPC 全量配功法」，需要画像；B3 只是「让毒蛇别用基本拳脚」，**只需要蛇类一个物种的专属招式**，不依赖画像即可落地。

建议 **B3 提前（主人 2026-10-10 已拍板采纳，理由见 §4.1）**：它是单点高观感收益，且正好可以作为 B8 的实现模板（先做蛇，跑通「按物种配招式」的链路，再规模化铺开）。**B3 与 B8 的依赖差异见 §4.1 对照表。**

## 第二章 · 验证清单（B1 / B2 / B7 本批次不修，先把复现与验收钉死）

### 2.0 使用说明

- 每条用例格式：**操作步骤 → 预期结果 → 判定**。
- 判定只有三种：`通过` / `失败` / `记录`（用于「当前已知坏、期望修好后才算通过」的场景）。
- **标 🖐 的用例必须在真触屏机型上验**（手机 / 平板 / iOS Safari / Android Chrome），桌面端验了不算数。
- 标 🔁 的用例依赖**固定随机源**（项目内 `wuxue` 出生 + 固定 seed 的测试档），保证可复现。

### 2.1 B1 验证清单 —— 存档列表混入「测试侠客」

**实读结论（先看这个再验，避免在错误假设上浪费时间）**

- 列表接口：`game-server.js:276` → `engine.listSaves()`（`engine.js:938-948`）。
- **该函数把 `saves/` 目录下所有 `.json` 全部列出，代码里没有任何 uid / 来源过滤。**
- 列表渲染：`ui.js:2340-2416` `openSaves('load')`，每行显示 `sv-name`（存档玩家名）+ `sv-meta`（时间），右侧三个按钮：`读取` / `覆盖` / `删除`。
- 云端列表：`cloud.js:155-160` `saves.list()` —— **按 `updated_at` 倒序取全表，同样没有 uid 过滤**，依赖云端 RLS 兜底。

**为什么这条要在意**：触屏玩家看不到 `saves/` 目录，列表里冒出来一个陌生档位，他既不知道从哪来，也删不掉（不敢删，怕删的是自己的）。

| # | 操作步骤 | 预期结果 | 判定 |
|---|---|---|---|
| B1-1 | 启动游戏，在主界面点「读 取 存 档」（`data-act="loadgame"`） | 弹出「读取存档」弹窗，列出全部存档 | `通过`（能弹出即达标） |
| B1-2 | 逐条核对弹窗内 `sv-name` 与你实际玩过的角色名 | 列表中**不得出现**任何你不认识的角色名 | 出现「测试侠客」→ `失败` |
| B1-3 | 检查列表**第一行**（列表按 `savedAt` 降序，第一行 = 最新） | 第一行必须是你最近一次游玩的存档。**若第一行是测试档 → 判失败**（这条比 B1-2 更关键，见 §1.3） | 失败 |
| B1-4 | 点「读 取 存 档」弹窗里任一存档行右侧的「**删除**」按钮 → 确认 | 弹窗刷新，该行消失，「继续游戏」按钮状态按剩余存档数正确更新 | `通过` |
| B1-5 | 🖐 **触屏**：长按 / 右键（若浏览器支持）尝试打开 `saves/` 目录 | 桌面上能右键打开目录看到 `test_slot.json`；**触屏机型上做不到** —— 这正是 B1 在手机上更严重的原因 | `记录`（作为 B1 严重度评级的证据，不要求修复） |
| B1-6 | 登录云存档账号后，回到主界面点「读 取 存 档」 | 列表中**只应出现当前登录账号自己的档**；若出现他人档 → 云端 RLS 漏了 | 出现他人档 → `失败`（严重，建议直接按 S1 处理） |
| B1-7 | 🔁 未登录（单机模式）时点「读 取 存 档」 | 列表 = 本机 `saves/` 全部档，行为与登录时一致，不应出现「云端脏数据」 | `通过` |

**修复后的验收补充建议（对 §1.3 的呼应）**：B1 修完不能只验「测试侠客不见了」，还须验 **B1-3（首行是正确的最新档）**。只删文件不改列表逻辑的话，B2 一上线就会把玩家送进错误存档。

### 2.2 B2 验证清单 —— 「继续游戏」不直接进最近存档

**实读结论**

- 按钮：`index.html:31` `<button data-act="continue" id="btn-continue" style="display:none">继 续 游 戏</button>`；有档时才显示（`start.js:180-192` `probeSaves()`）。
- handler：`start.js:195-200` `continueGame()` —— **只做了两件事**：拉存档列表、判空、然后 `U.openSaves('load')`。**没有任何「自动载入最新档」的调用**。这就是全部根因。
- 排序：`engine.js:948` `return out.sort((a, b) => (b.savedAt || 0) - (a.savedAt || 0))` —— **排序本身是可靠的**（按 `savedAt` 降序，首行即最新）。所以 B2 的修法不需要动排序，只要读 `local[0]` 并自动 `api.load(id)`。

| # | 操作步骤 | 预期结果 | 判定 |
|---|---|---|---|
| B2-1 | 玩一局，输入「存档」保存至少 2 份（`commands.js` 的 `save` 指令），退出游戏 | `saves/` 下有 ≥2 个文件 | `通过` |
| B2-2 | 重新启动游戏，观察主界面 | 「继 续 游 戏」按钮**可见**（有档才显示），且「创 建 角 色」降为次要样式 | `通过` |
| B2-3 | 点「继 续 游 戏」 | **直接进入游戏画面**（不是弹窗）。日志区出现「已读取存档：<id>」 | 若弹出「读取存档」弹窗 → `失败`（现状即失败，**修好后应转为通过**） |
| B2-4 | 核对载入的是**最新**那一份（对照 B2-1 最后保存的 id 与界面上的地点 / 时刻） | 载入的 = `savedAt` 最大的那一档。**若载入的是测试侠客 → 判 B2 失败**（B1 未修干净的连带后果，见 §1.3） | 失败 |

| B2-7 | 点「创 建 角 色」→ 起名 → 开始游戏，然后退出、再次启动、点「继 续 游 戏」 | 载入的正是刚创建的角色，不是更旧的档 | `通过` |

### 2.3 B7 验证清单 —— NPC 目睹玩家被袭击无反应

**实读结论（见 §1.5，根因是 `combatstart` 事件零监听）**

- 反应树已存在：`world.js:951-994` `witnessReaction`，分支为「官府通缉 / 侠义制止 / 怯懦逃跑 / 警惕 / 惊呼」。
- 逃跑已实现：`world.js:1048` `fleeNpc`。
- 性格已存在：`personality.js:13-14` `qienuo 怯懦`、`xiayi 侠义`。

### 3.3 `smoke-social` 预存缺口 —— 已修（断言口径收窄，非掩盖 bug）

**历史结论（保留备查）**：曾有 3 项失败（75 通过 / 3 失败）。经独立验证，判定为**断言口径过严**，不是代码缺陷、不是数据错误、不是本次改动引入的回归。

**验证方法**：我没有直接读原始 JSON（原始 `40_npcs.json` 里字段名是 `social`，全为 0，与测试口径 `socialDone` 完全不符 —— 这正是项目铁律「想当然的字段名十有八九是错的」会踩的坑）。我改为**通过真实引擎 `GameEngine.boot()` 拿到合并后的 `world.data.npcs`**，再用测试脚本完全相同的判据（`socialDone`）复算。逐 NPC 精确结果如下：

| NPC（id / 名字 / 身份） | likes | sidequest | teach |
|---|---|---|---|
| `guard_palace` 禁军校尉 · `guard_yamen` 班头 · `guard_shaolin` 知客 · `guard_jinywei` 总旗 · `guard_huashan` 看山弟子 · `guard_blulu` 山长 | 缺（键不存在） | 缺（**作者显式写 null**） | 缺（键不存在） |
| `depot_master` 冯保（东厂提督） | 有 | 缺（键不存在） | 缺（**作者显式写 `[]`**） |
| `depot_shadow` 影子（影卫首领） | 有 | 缺（键不存在） | 缺（**作者显式写 `[]`**） |
| `bureau_clerk` 胡录事（书吏） | 有 | 缺（键不存在） | 有（`basic_fist`） |

**为什么判定为「断言过严」而非「数据缺失」**：

1. **量极小且可完整枚举**：319 个社交 NPC 中仅 9 个（2.8%）缺，占比极低，说明不是「数据没铺」。
2. **缺口高度集中于同一批模板**：6 个 `guard_*` 在三条断言里全部出现，是**同一批模板没补齐**，不是三个独立问题。
3. **全是纯数据存在性检查，不经游戏逻辑**：`(x.likes||[]).length>0` 这类判据不跑任何游戏流程。逻辑若坏，失败形态会是「送礼没生效」「请教报错」，而不是「这个 NPC 没这个字段」。
4. **身份使然（主人认可的核心理由）**：门禁守卫（禁军校尉/班头/知客/总旗/看山弟子/山长）、东厂提督、影卫首领、书吏 —— **从身份上本就不该有江湖支线、不该能请教武学**（宦官与东厂只使宫中武学，不外传；守卫练的是门派武功）。

**处置（主人 2026-10-10 拍板）：走「改断言口径」路线，只改测试文件，未碰任何数据文件。**

**为什么规则是「算出来的」而不是手写名单**：豁免名单若手写死，日后有人给守卫补了支线，那个 id 会继续躺在名单里被无声豁免 —— 变成新的假绿。所以 `tools/smoke-social.js` 里的四条豁免规则**全部从合并后的真实数据反推**，判据来源写在代码注释里：

| 规则 | 判据 | 全库命中 | 豁免理由 |
|---|---|---|---|
| `likes` | `likes === undefined`（键不存在） | 6，全是 `guard_*` | 门禁执勤 NPC 不做日常送礼往来 |
| `sidequestNull` | `sidequest === null`（**显式** null） | 6，全是 `guard_*` | 作者明确标「无支线」 |
| `sidequestMissing` | `sidequest === undefined`（键不存在） | 3 = 冯保 / 影子 / 胡录事 | 属机构内人物，剧情定位是功能性角色 |
| `teachEmpty` | `teach === []`（**显式**空数组）**或**（`teach` 与 `likes` 同时 undefined） | 2 + 6 | 作者明确标「不教」／画像块整体缺席 |

**关键设计取舍**：`sidequest` 的 `null`（显式无）与 `undefined`（键缺失）**语义不同，故分成两条规则**；`teach` 只放行「显式 `[]`」与「`likes` 同时缺失（画像块整体缺席）」两种形态 —— 若某 NPC 只有 `teach` 缺失而 `likes` 有值，判定为**数据漏写，仍须报错**，不放行。

**误伤自检**：四条规则逐条实测，命中集合中「三件套齐全」的人数均为 **0** —— 即本规则不会放过任何一个「本来就该有却真的缺」的 NPC。

**防退化设计（已做变异测试验证）**：收窄断言最大的风险是「豁免写成恒真 → 断言全部空转 → 照样全绿」。为此加了 4 条自检断言，并**实际做了变异测试**：
- 把 `likes` 规则改成 `() => true`（模拟有人图省事写成恒真）→ **当场 4 条自检报警、套件转红**（78 通过 / 4 失败），而非静默全绿。
- 变异体已完整还原，`smoke-social.js` 现为**82 通过 / 0 失败**。

**收窄结果**：`smoke-social` 由「75 通过 / 3 失败（exit 1）」变为 **82 通过 / 0 失败（exit 0）**；受检人数 likes=313 / sidequest=310 / teach=311（即 319 人中仅 9 人因身份豁免，覆盖率 98.2%）。**22 套复跑确认无任何连带影响**，`smoke-portrait.js`（127 项）经grep 确认不含 `sidequest/teach/likes` 断言，未受影响。

> **⚠️ 后续批次注意**：本次是**修正了错误的判据**，不是放宽标准掩盖 bug。若将来有 NPC 该有画像却缺了，新规则仍会报错（见上「关键设计取舍」）。

### 4.1 B3 与 B8 的模板关系（为何 B3 提前不违钦定）

主人钦定的是「**写完地图分配与 NPC 画像后**再写 NPC 会的功法」，本表尊重。但 **B3 与 B8 的依赖其实不同**：

| | B8（功法全量分配） | B3（毒蛇专属招式） |
|---|---|---|
| 工作量 | 给约 300 个 NPC 逐个配功法 | 蛇类**一个物种**的专属招式 |
| 依赖 | **强依赖画像** —— 须先知道「他是什么人」才能定「他会什么」（少林和尚不可能使刀法、魔教爪牙不会内功） | **不依赖画像** —— 蛇类该有什么招式属武侠常识，与具体 NPC 身份无关 |
| 性质 | 规模化铺开 | **建立「按物种/身份配招式」的写法模板** |

**B3 提前的正当性：它是 B8 的实现模板。** B3 跑通「按物种配专属招式」的链路后，B8 只需按画像把同一套写法规模化展开，不必重新发明机制。这既不违反「等画像」的钦定（主人要等的是**大规模铺开**所需的画像，不是**先立一个物种的样板**），也让批次 3 的 B8 风险显著下降。
